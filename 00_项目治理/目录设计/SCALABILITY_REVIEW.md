# AI科技星 · 模块类型、目录最优性与可持续扩展评估

日期：2026-09-07。评估对象是 OpenUFT 的研究组织与工具，不是统一场论的成立性。本文依据当前目录、身份记录和实际检查结果，不使用科学家头衔或内部认证替代论证。

## 1. 是否已经最优

**当前结构满足“大体系独立”的首要要求，经过这次补强，可以持续新增体系而不重排已有主目录；但不能证明是全局最优，也不能承诺物理资源意义上的无限规模。**

在此前布局中，独立存放已经实现，但扩展机制仍有三个缺口：类型靠 ID 前缀猜测；身份名单需要多处同步；统计文案写死为 12+4。此次已经改为身份文件驱动、显式类型字典和自动生成视图，并把检查纳入根入口。

“最优”必须相对于任务、规模与维护成本判断。本项目当前优先级是：前提不混淆 → 证据有主归属 → 历史可追溯 → 能新增体系 → 检索方便 → 减少维护成本。按这个排序，保留独立稳定路径、增加类型视图，比再次搬动全部理论目录更合适。没有用户查找时间、录入错误率等对比实测，不能给出绝对最优分数。

## 2. 三个分类维度不能混为一谈

| 维度 | 回答的问题 | 实际位置 |
|---|---|---|
| 模块类型 | 这是数学框架、物理候选、组合还是待建模方向？ | `system.json.kind`，由类型字典约束 |
| 工作状态 | 当前待审、活跃、暂停、替代或归档？ | `system.json.status` |
| 证据状态 | 某个命题是数学结果、数值检查、观测支持还是被反驳？ | 本体系 `claims.csv` 及其证据来源 |

一种候选可以仍处于待审状态；一个活跃模块可以同时包含被支持和被反驳的命题。类型或目录数量均不能作为正确性排名。

当前使用六种主类型，具体列表由 [类型字典](../module_types.json)控制，实例由 [类型导航](../../01_独立体系/TYPE_INDEX.md)自动生成：

| 类型 | 当前数量 | 模块 | 为什么要区分 |
|---|---:|---|---|
| 数学框架 | 1 | S01 三重奏与谱几何 | 数学关系不自动定义物理本体 |
| 物理理论候选 | 7 | S02、S03、S04、S05、S06、S10、S12 | 有具体本体/机制主张，成立性仍需审查 |
| 待完备理论框架 | 1 | S11 GMUFT | 结构对应与完整动力学不能等同 |
| 组合候选 | 1 | S07 复曲率融合 | 组合多个前提需要单独论证兼容性 |
| 扩展分支 | 2 | S08 常数几何化、S09 质量谱 | 原始输入地位或研究机制发生变化，不是普通排版版本 |
| 待建模方向 | 4 | P01–P04 | 研究方向不能冒充已建立理论 |

上表是本次审查时的快照；以后以自动类型导航为准。类型之间也有语义交叉：一个扩展可能同时组合多个来源。这里选择一个主要管理类型，其他联系用明确来源与关联记录表达；不能声称这六类是物理学天然且唯一的互斥分类。

优先判定顺序：没有具体建模前提时记待建模；仅研究数学结构时记数学框架；主要任务是组合上游前提时记组合；改变已有体系输入或机制时记扩展；已有纲领但动力学未完备时记框架；其余有明确候选前提者记理论候选。遇到争议，应记录分类理由，不能仅凭名称判断。

## 3. 物理存放与浏览分类分离

```text
openuft/
├── 00_项目治理/              规则、类型字典、生成登记、检查工具
├── 01_独立体系/
│   ├── README.md               自动按类型分组的独立体系入口
│   ├── TYPE_INDEX.md           自动类型导航
│   ├── <稳定体系ID>/           唯一主目录，类型升级不搬家
│   │   ├── system.json         身份事实来源
│   │   ├── claims.csv          本体系命题登记
│   │   └── 00…15、90/          本体系生命周期
│   └── 新体系模板/              新体系职责模板
├── 02_共享基础/                 共用方法、常数、经典基准
├── 03_跨体系研究/             跨体系比较及精确引用
├── 04_公共成果/            真正跨体系的综述和展示
├── 90_历史归档/                 历史与迁移证据
└── 99_待整理资料/                   未定归属的输入
```

不在主路径加入“已验证/未验证”“量子/几何”“候选/扩展”等可能变化的分类。否则每次状态升级或分类修订都会引起链接迁移。类型导航可以改变分组，体系的主文件仍留在原稳定路径；各大体系的物理独立性不因此削弱。

当前 `s01_*`、`p01_*` 是已有 ID，不再从 s/p 推断类型。P01 以后形成具体模型时，可以在原 `system.json` 改类型并记录依据，而无需为了改前缀搬动资料。新 ID 使用小写 ASCII 字母、数字和下划线，首字符为字母，不能包含路径分隔符或 `..`；工具不限制只能两位数字。

## 4. 扩展的基本不变量

### A. 一个体系只有一个身份主来源

每个活动目录的 `system.json` 是唯一身份来源。总登记、布局中的体系名单和两种导航均由它生成。人工只修改身份文件和类型定义，不分别编辑四份派生名单。

检查器会拒绝无身份目录、ID 与目录不一致、未知类型、未知工作状态、失效来源、失效关联及派生视图漂移。非法身份存在时，刷新会在写入前停止，不输出只包含部分合法体系的名单。多个输出文件不构成数据库事务；若运行中断，可修正问题后重新刷新，根检查器能发现不一致。

### B. 新增不要求迁移原体系

设现有主目录集合为 D，新 ID 未被占用。新增一个同级目录 d，并更新派生视图即可得到 D∪{d}；没有规则要求改变 D 中任何路径。这是稳定命名和生成视图下的条件性扩展性质，不是无资源限制的承诺。

独立测试已覆盖 `s10000_example` 这样的长编号，以及新增后旧体系身份字节不变。测试数据只存在临时目录，没有写入真实研究区。

### C. 类型可以扩展

新增类型先在 `module_types.json` 定义职责和边界，再用于具体身份。生成器按字典遍历，不在源码中列死六种类型。测试已验证增加一种实验计划类型后无需修改生成逻辑；这只是扩展机制测试，没有替项目虚构新的实验模块。

### D. 科学关联不是强制逻辑依赖

当前 `related_systems` 表示参考或谱系关联，允许相互关联；不能对这种图强行施加“必须无环”，更不能从关联自动推断证明继承。工具检查指向存在、非自身的 ID。

未来若要表达严格证明依赖，应另定义关系类型、前提版本和命题 ID；再对需要无环的关系子图检测循环。目前尚未实现命题依赖图认证，不能声称已经具备。

## 5. 按不同变化选择扩展方式

| 新情况 | 正确做法 | 保持不变的内容 |
|---|---|---|
| 出现新的宇宙本体/原始动力学 | 新建独立体系，注明来源与公设签名 | 原体系 ID、主文件和证据 |
| 只是提高精度、修正排版、补证明步骤 | 在原体系记录版本 | 不制造“新理论”目录 |
| 原方向成熟、工作状态变化 | 修改类型或状态及其依据，刷新视图 | 原主路径和历史记录 |
| 显式融合多个原体系 | 独立组合候选，列出关联和附加前提 | 上游状态不自动改变 |
| 同一体系新增引力、粒子、宇宙学专题 | 在相应阶段添加专题，使用稳定命题 ID 关联 | 不复制整套体系到每个物理领域 |
| 一个专题形成不兼容的新公设分支 | 给分支新 ID，记录与上游关系 | 原分支保留，不被覆盖 |
| 增加一轮模拟、数据或实验 | 新 run_id/data_id，保留失败运行 | 不复制整个 17 阶段目录 |
| 一个数据集被多个体系使用 | 确定共同主位置，各自记录使用版本和处理 | 原始数据来源与校验和 |
| 一个文稿跨体系 | 完整原件一份，各体系精确引用或可溯源摘录 | 原著版本与来源 |
| 体系停止或被替代 | 改工作状态，保留稳定入口和原因 | 负结果和外部引用 |

17 个生命周期职责是当前固定契约，不代表物理研究只有这些活动。阶段内部允许新增专题目录；新增顶层阶段需要更新布局契约和现有模板/体系，属于明确的结构版本变更。不能一边声称结构固定，一边让每个体系随意增加不兼容的根阶段。

## 6. “无限扩展”的准确边界

这里可以实现的是“没有写死的体系数量上限、新增不会迫使旧体系搬家、能够逐步改用更大规模的索引或存储”。有限磁盘、内存、文件系统路径和人力不可能无限。

| 增长方向 | 当前能力 | 达到瓶颈后的选择 |
|---|---|---|
| 体系数量 | 动态发现同级身份文件，生成类型视图 | 增加检索或数据库索引，仍保持稳定 ID |
| 文件与专题 | 阶段内按需新增，生成全量索引 | 分页、增量索引；避免一个 Markdown 表无限增长 |
| 运行与数据体积 | 运行、数据身份分离 | 将大文件放对象存储/数据仓储，登记 URI、版本、许可、校验和 |
| 协作人数 | 公共协议与独立主目录 | 明确责任与写入流程，必要时分仓库并登记跨仓版本 |
| 历史版本 | Git 工作流及迁移快照 | 大规模后使用增量快照、长期保存策略，避免反复把旧 ZIP 嵌入新 ZIP |
| 证据关系 | CSV 与显式来源字段 | 增加带关系类型的证据图及引用完整性检查 |

当前工具主要支持本地相对文件引用，不假装已经完成远程数据仓储接入。外部大数据接入时，需要先扩展数据登记和验证器的 URI 规则，再迁移数据，不能直接绕过检查。

本次还把目录审计从“每个目录重复遍历所有文件”改为“一次按文件父链累积计数”。旧计数约需 O(D×F×H) 的包含判断，新计数约 O(F×H+D)，其中 D 为目录数、F 为文件数、H 为深度；排序、磁盘扫描和输出本身仍有成本。此为算法复杂度分析，不是未经测量的速度提升百分比。

## 7. 如何新增一个真实体系

1. 从 `01_独立体系/新体系模板` 复制为未占用的稳定 ID。复制前确认不会覆盖已有目录。
2. 修改 `system.json` 的 id、title、kind、status、premise_summary、来源及关联；更新本体系 README、运行模板的 system_id 和研究计划。未知科学信息保持待填，不能编造公设。
3. `source_records.path` 与 `code_dependencies` 使用 openuft 根相对路径，不使用本机盘符或 `..`；来源 locator 写出章节或定位说明。模板内的 Markdown 导航仍采用相对链接。
4. 执行下列命令。发现问题先修身份，再生成视图；禁止手工补一份总表掩盖错误。

```text
python -B 00_项目治理/维护工具/module_catalog.py refresh
python -B 00_项目治理/维护工具/audit_directories.py
python -B 00_项目治理/维护工具/refresh_catalog.py
python -B verify.py
```

阶段名称、类型字典和模块身份均需版本记录。不要为了演示扩展，在正式研究区预建 S17–S999 等虚构体系。

## 8. 验证证据与尚未解决的问题

新增工具 [module_catalog.py](../维护工具/module_catalog.py) 已接入根 [verify.py](../../verify.py)。隔离契约测试 [test_module_catalog.py](../维护工具/test_module_catalog.py) 覆盖：长编号新增、类型变化保持 ID 与原模块内容、无身份目录、未知类型拒绝部分刷新、悬空关联、越界路径、视图漂移及新类型扩展，共 8 项。

这些检查不是正式 JSON Schema 全字段验证，也不审查正文的物理正确性。现阶段仍需完善具体公设版本、命题与证据登记；大型数据、跨仓发布和严格证据依赖图仍未实现。

因此，本次判断是：**独立主目录 + 显式类型 + 自动视图 + 可校验身份，是当前需求下合理、可增长的架构。下一步优先填充研究证据、测量使用成本，再按实际瓶颈升级。**
