## 1. 为什么需要一份"发布布局"

本项目的 git 根目录是**上层工作区**（my_lib），`openuft/` 只是它下面的一个子目录。
而 GitHub 上的独立仓库需要让 `openuft/` 的**内容**位于仓库**根**，
这样 `README.md` 是仓库首页、`verify.py` 就是首页那行命令。

于是有两套布局，内容同源、层级不同：

| 布局 | 形态 | 用途 |
|---|---|---|
| **主仓库布局** | `<工作区根>/openuft/00_项目治理/…` | 日常研究、与工作区其它内容共存 |
| **发布仓库布局** | `<仓库根>/00_项目治理/…` | 对世界开放，独立克隆与协作 |

两者之间由脚本做**子树去前缀镜像**，不做任何人工搬运。

## 2. 发布布局为什么用中文目录名

`verify.py` 有一条硬约束：**仓库内任何目录名必须含中文字符**
（见 [目录约定](layout.json) 与 `layout.json` 的既有 section 名）。
历史上曾出现过一个把目录改为英文（`00_governance/01_systems/…`）的
拆分方案，它与该约束冲突、会令校验器失效，因此**未采用**。

结论：发布布局保留中文目录名，与主仓库完全一致。
对不习惯中文目录名的贡献者，请参考 [国际参与说明](../国际参与说明.md)。

## 3. 一条命令完成发布

```bash
# 只做镜像 + 干净副本校验（安全，不动远端）
python -B 00_项目治理/维护工具/publish_standalone.py

# 校验通过后再推送
python -B 00_项目治理/维护工具/publish_standalone.py --push
```

脚本 `维护工具/publish_standalone.py` 只依赖标准库，流程为：

1. 取 `HEAD:openuft` 的 tree 对象（**只镜像已提交内容**）；
2. 在独立 `git worktree`（默认工作区同级的 `_openuft_publish`）里，
   用 `git read-tree --reset -u` 把该子树摊到副本根；
3. **在干净副本内**运行 `verify.py`，不通过就中止；
4. 提交到发布分支 `openuft-standalone`；
5. `git push --dry-run` 预演；确认是 fast-forward 后才真正推送。

## 4. 为什么必须在"干净副本"里校验

主工作区里有三样东西，在 `git clone` 出来的仓库里**不存在**：

- 未提交的新文件（`git status` 里是 `??`）；
- 被 `.gitignore` 排除的文件；
- **空目录**（git 根本不表达空目录）。

这三样都曾让"克隆即可校验"这一承诺失效。已发生并已修复的实例：

| 实例 | 症状 | 修复 |
|---|---|---|
| 4 个迁移快照 zip 被 `*.zip` 规则排除 | 克隆后 `verify.py` 直接 `FileNotFoundError` | `.gitignore` 加否定规则并入库 |
| 5 个空 `结果/` 目录 | 克隆后 5 处 `Broken link`，整体 `FAIL` | 各加 `.gitkeep` 占位 |

**所以：只信干净副本的结果。** 在主工作区跑出的 `PASS` 不能作为发布依据。

## 5. 发布前检查清单

- [ ] 所有要发布的内容**已提交**（工作区里的改动不会进发布仓库）
- [ ] `python -B verify.py` 在主工作区通过
- [ ] `publish_standalone.py` 的干净副本校验通过
- [ ] `git push --dry-run` 显示为 fast-forward（含 `..`、不含 `+`）
- [ ] 本次发布的实质变化已在提交信息里说清

## 6. 本项目的发布原则

1. **不重写历史**：发布走 fast-forward；脚本遇非 fast-forward 会停下，不自动强推。
2. **不美化发布内容**：已证伪的结论照旧以 `falsified` 发布
   （见 [独立体系](../01_独立体系/README.md) 各体系的 `claims.csv`）。
3. **发布不等于认证**：内容进仓库不代表任何理论成立，见
   [统一架构总纲 T3](../06_统一体系层/统一架构/统一架构总纲.md)。
